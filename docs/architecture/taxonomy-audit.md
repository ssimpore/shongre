# Canonical taxonomy v1 consolidation

Updated 2026-09-09. The working tree consolidates runtime taxonomy into **v1**, with separate editorial revisions and backend-owned PostgreSQL authority. Migrations were executed only on the repository-owned local database. Production and hosted environments were not changed. Native device verification and exhaustive journey coverage remain outstanding; this report does not certify the entire request as complete.

## Inventory and selection

[The inventory](generated/taxonomy-consolidation-inventory.json) contains 374 records, preserving the initial 295 reference records, their consumers and proposed dispositions and adding final locations/dispositions and affected files. Initial `consumers`/`runtimeReachability` fields preserve the pre-change inventory; `finalLocation`, `finalConsumers` and `finalDisposition` describe the resulting system. The most complete existing implementation was the published relational taxonomy previously called V4. Its hierarchy, resolver, governance, dependencies, projections and revision repository were consolidated incrementally.

The competing sources found were the unversioned/legacy category catalogue and validator; shared generated V4 identity/card/resolver modules; the runtime private V4 bundle; duplicate test repositories; and separately read/administered vehicle, property, course and employment reference catalogues. V3 identities and earlier taxonomy versions also appeared in import crosswalks and applied migration history. Those historical records do not remain executable taxonomies. Unrelated API `/api/v1`, domain schema versions, business product identifiers and dependency versions are preserved.

The controlled v1 input contains 19 roots, 302 categories, 213 listing types, 349 attributes, 56 groups, 110 option sets, 753 options, 92 parent links, 10,859 bindings, 217 dependencies, 535 validation declarations and 292 aliases. It also preserves quarantined country/seller/reference review records. [The generated import report](generated/taxonomy-v1-import-report.json) and [coverage matrix](taxonomy-field-matrix.md) own structural detail. Structural coverage is not certification of every leaf's domain content, translations or legal policies.

The same v1 publication now contains 144 domain reference entries: 10 vehicle types, 6 vehicle field definitions, 9 vehicle make/model entries, 11 property types, 14 property field definitions, 5 property rules, 15 course subjects, 5 course levels and 69 employment dictionary entries. Existing row identities and foreign keys remain stable. Domain-specific names describe resources within v1, not separately selectable taxonomy versions.

## One publication and administration boundary

`taxonomy_configuration` selects the draft revision and one immutable `taxonomy_publications` snapshot. Relational hierarchy/attribute/option/binding/market tables and the nine domain reference tables are authoring resources. `read_taxonomy_draft()` derives the document from these rows. `TaxonomyGovernanceService` validates, saves, previews, publishes and rolls back that document through `PostgresTaxonomyPublicationRepository`.

`PublishedTaxonomyService` checks the database pointer before returning a revision/checksum-bound resolver. Database errors propagate; they cannot select a compiled catalogue or return an unchecked cached taxonomy. `TaxonomyV1Service` owns identity/alias lookup, parent traversal, option dependencies, validation and projections. Import compilers and isolated test scenarios explicitly supply their own input and revision; they are not application fallbacks.

Web, native and server rendering use generated transport operations. Public taxonomy endpoints are under `/api/v1/taxonomy/v1`; the protected admin workflow remains `/api/v1/admin/taxonomy`. The four vertical catalogue endpoints retain their domain URLs and now have concrete generated response schemas. Their reference sections are read from the same published v1 revision. SQL course discovery also reads the published reference projection. Anonymous and authenticated database roles cannot read draft reference tables.

The taxonomy editor exposes `referenceEntries` alongside the existing hierarchy, field, option, dependency, validation, alias and presentation resources. Vehicle, property and course screens link to that editor; their independent classification writes were removed. Commercial pricing, quotas and eligibility remain in their owning domains. Vehicle activation still checks the existing commercial market gate. Reference identity, field type and unit changes require reviewed migrations; unknown parents, cycles and invalid domain values reject publication.

A reference export contains each editable field once. Import rebuilds its derived `public_payload`, retaining payload-only information. The 144-entry round-trip test compares the complete resulting database write against the original. Editor imports remain revision-checked batches of at most 200 records: an interrupted multi-batch import leaves a visible draft and never publishes automatically. Existing MFA, recent-authentication, capability, audit and optimistic-conflict protections remain authoritative.

Taxonomy-derived HTTP responses, including course catalogues, use `no-store`. The existing external cache adapter emits invalidation tags without acknowledging delivery; shared caching must remain disabled until that operational capability exists. Search cursors carry their taxonomy revision and reject continuation after publication. Public tree responses include the published aliases, SEO metadata and revision. Sitemap and direct category navigation resolve that API data instead of a bundled catalogue.

## Specialized publication and display

Vehicle and property catalogues project ordered, active public option sets from the same v1 revision. Vehicle make/model selectors read the published reference entries and constrain children by parent/type; changes clear incompatible model/generation/trim values with feedback. Fuel, transmission, condition and history selections are validated again on submission. Caller-supplied make/model labels are replaced by published labels. Vehicle/property/course cards and vehicle comparisons use API-projected characteristic labels; broad historical category identities stay broad. Non-kilometre vehicle counters remain in the typed public payload and are omitted from the canonical kilometre card field rather than displayed with the wrong unit.

Property publishing preserves the domain reference equipment options, including `accessible`, and its uppercase DPE/GES wire identities. The general property option sets and domain reference fields are distinct typed resources in the same v1 publication; their historical wire identities are not silently remapped. The property HTTP adapter now maps flat view state to the existing nested draft payload. It retains stored fields, currency, energy metadata, document records and extra domain attributes. The local database contained zero property drafts (including zero flat drafts) before this correction. Exact addresses and private document keys are sent only through the authenticated API; no browser draft storage was introduced. Monetary period suffixes and commercial/account workflow choices remain domain presentation, not taxonomy catalogues.

The specialized vehicle/property/employment/tutor/learner editors remount on account or market change and ignore stale hydration responses. Catalogue failures expose retry instead of a permanent loading state. Course subject changes clear incompatible levels; employment profession changes clear incompatible specializations. Backend course writes validate published subject/level relationships and offer markets. Existing unchanged profile references stay readable; changed selections are checked. Employment submission validates dictionary kinds and specialization parents, and derives labels from the published reference data. Tutor-profile mutation now declares the existing central market header in OpenAPI. Course workflow draft reads/writes/deletion receive an explicit market; the mutable account→last-read-market maps and implicit France fallback were removed. Actor identity comes from the authenticated API principal, so unused caller account/display-name arguments were removed from these Web contracts and consumers.

Vehicle and property detail pages render the API’s localized public characteristic projection, including stored history, condition and applicable equipment. The vehicle page no longer asserts that every listing is accident-free. Comparisons derive specification rows from those same public values, clear stale requests on market/selection changes, and expose API error/retry. The detail comparison link no longer inserts a fixture vehicle.

## Removed and deliberately retained material

Removed runtime material includes the V4 service path/symbols, legacy taxonomy validator/catalogue/test repository, shared V4 resolver/identity/card implementations, old public generated bundles and exports, hardcoded category icon map, obsolete public taxonomy operations, and four independent domain classification PATCH operations. Retired operations are the V4 tree/resolve/options paths; unversioned taxonomy root/node/children/attributes/slug/search-filter paths; the former header-navigation path (now under v1); and `PATCH /auto/admin/markets/{marketCode}/types/{type}`, `PATCH /education/admin/markets/{marketCode}/subjects/{subjectId}`, `PATCH /real-estate/admin/markets/{marketCode}/types/{type}` and `PATCH /real-estate/admin/markets/{marketCode}/field-rules/{ruleId}`. Their owned callers were migrated to v1 or the central editor; no blocking external consumer was identified in repository evidence. Active files/routes/tests/tooling now use v1 terminology. Removed generated outputs and their producers were migrated together.

Retained material has a concrete purpose:

- `backend/taxonomy/v1/` is controlled import provenance; PostgreSQL is authoritative after import. `reference-entries.json` preserves the imported reference baseline and does not feed runtime requests.
- `backend/taxonomy/generated/` and `packages/contracts/src/testing/` are explicit compiler/test inputs. Generated test responses are recorded from the backend resolver rather than a second shared resolver implementation.
- `backend/taxonomy/history/`, reviewed crosswalk fields mentioning earlier versions, applied SQL migrations and immutable publication/conversion records preserve historical evidence. They cannot select a previous runtime implementation.
- Stable domain identity constants and business enums remain intentional contracts for specialized domain routes. They contain no editable labels, hierarchy, options or fallback catalogue. Commercial product/provider/finance compatibility is outside taxonomy version cleanup.
- Domain-specific relational authoring tables preserve foreign keys. Their values publish through v1; independent direct readers/editors are gone.
- Old public URLs remain canonical alias mappings. Private/internal listing attributes remain excluded from public read projections.

`make taxonomy-check` runs architecture regression tests and generation/integrity checks. The guard rejects non-v1 runtime taxonomy, runtime generated/test catalogue imports, source-selection branches, client resolvers/direct taxonomy queries, fallback catalogues, direct reads of reference authoring tables and known duplicate dictionaries. It scopes historical migration/test exceptions and unrelated versions explicitly. The Web bundle budget permits **zero embedded generated taxonomy data**. AGENTS.md records the durable authority, revision, import, cache and reference-publication rules.

## Listing-sheet relevance, identity and help text

Added 2026-09-09, after the consolidation above. The consolidated sheets were structurally complete but three content defects were measurable in the generated matrix.

**Irrelevant fields.** The workbook bound a vertical's attributes to every leaf of that vertical, so the publication form, filters and detail page offered fields that do not describe the product: `electronics.audio_hifi.photo` published "Console platform", "Game genre", "Carrier lock status" and "IMEI"; `leisure_culture.gastronomy.wine_gastronomy` published "ISBN / EAN", "Author" and "Handedness"; `home_garden.decoration.linens` published "Appliance capacity" and "Energy efficiency class". [`backend/taxonomy/v1/leaf-applicability.json`](../../backend/taxonomy/v1/leaf-applicability.json) is the reviewed record: 31 decisions naming the leaves each attribute describes, each with a bilingual justification for the leaves it does not. The compiler narrows the imported bindings to that record and reports the remainder as justified not-applicable decisions, now counted per leaf in the [coverage matrix](taxonomy-field-matrix.md). 209 bindings were retired across electronics, culture, home & garden, energy transition and baby & family. `appliesTo` must stay within the imported set unless the decision also names an `extendFrom` leaf: two decisions do, widening repair history from smartphones to laptops, tablets and smartwatches, which resell with the same replaced-part questions. No leaf lost a field its own review kept, and 22 leaves that legitimately share their vertical's attributes were left whole.

**Duplicated identity and labels.** Projection rows carried their own copies of labels, which had drifted from the definitions they present. All six phone reference and repair fields rendered as "Battery health" on detail pages and as "Brand" in filters, five of them shared the single filter id `electronics.smartphones.phones.listing|brand`, and 8,990 detail rows carried the French group label as their English section label even though 53 of 56 groups already had an English one. Filter identity, field labels and detail section labels are now derived at compile time from the attribute and its group, so one authored label serves every surface.

**Placeholder help text.** 322 of 349 attributes carried one generated sentence — « Caractéristique canonique ‹ X › réutilisable dans les catégories applicables. » — copied unchanged into `en-US`, so no publication field offered usable guidance in either language. [`backend/taxonomy/v1/attribute-help.json`](../../backend/taxonomy/v1/attribute-help.json) replaces all 322 with authored French guidance and a real English translation. The matrix gap "English help text contains copied French prose" now applies to zero leaves, down from all 213.

`00131_taxonomy_v1_field_relevance.sql` applies the same reviewed records to an existing database with set-based SQL, deriving labels from the canonical tables rather than restating them. It closes retired bindings with `effective_until` instead of deleting them, so historical listings stay readable, and archives each one to `taxonomy_migration_records`. It was prepared and applied against the repository-owned local database only: 209 bindings retired, 6 added, 322 help texts authored, one new publication revision, 42 listings and every stored value unchanged. `make taxonomy-migration-check ENVIRONMENT=local` now also fingerprints the database's binding, filter and help-text configuration against the compiled bundle, so a migrated database and a freshly seeded one are proven to converge rather than assumed to.

Regression cover: `taxonomy-leaf-applicability.test.ts` fails if a reviewed attribute is published outside its applicable leaves, if a removal lacks a bilingual justification, or if publication, filtering, cards, details and search stop agreeing on field identities; `taxonomy-v1-generated.test.ts` fails on a projection label or filter identity that is not derived from its definition, on a duplicate filter id, and on placeholder or untranslated help text. Both were confirmed to fail when the record is violated. Domain review of every leaf's subject-matter content, the 141 leaves whose domain reference data is still incomplete, and native-device journeys remain outstanding; this section does not certify them.
