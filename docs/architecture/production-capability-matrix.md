# Shongre production capability matrix

Initial audit date: 2026-08-25
Current launch review: 2026-09-01
Scope: Web, mobile, backend API/worker, PostgreSQL/Supabase migrations, shared
packages, infrastructure, CI/CD, security, compliance, operations and
documentation.

This document preserves the required **pre-implementation** classification and
adds the evidence-backed closure assessment below it. The initial matrix is
intentionally not rewritten: it remains the before-state against which the
implementation can be audited.

## Architecture discovered

Shongre is not a Django application. It is an npm-workspace TypeScript
monorepo composed of:

- Next.js 16 + React 19 Web application in `frontend/`;
- Node/TypeScript modular-monolith API and worker in `backend/`;
- Expo/React Native mobile application in `mobile/`;
- canonical contracts, access control, finance, feature, UI and design-token
  packages in `packages/`;
- 88 ordered PostgreSQL/Supabase migrations under
  `backend/supabase/migrations/`;
- one OpenAPI 3 contract with 461 runtime operations;
- Kubernetes, monitoring, backup/restore and release assets in
  `infrastructure/`, `scripts/` and `.github/workflows/ci.yml`.

The active dependency direction is already coherent:

```text
Web / Mobile -> shared contracts -> canonical /api/v1 -> domain services
             -> repositories/providers -> PostgreSQL / external providers
```

The smallest coherent target is therefore to finish and harden this modular
monolith. Replacing it with Django would duplicate every domain and migration,
break the generated client, and violate the requirement to reuse good existing
architecture.

## Status definitions

- `COMPLETE`: repository implementation covers the capability and its core
  architectural requirements.
- `PARTIAL`: meaningful implementation exists, but at least one production
  layer, provider, flow, verification or evidence requirement is absent.
- `MOCK`: only deterministic development behavior exists.
- `DUPLICATED`: more than one active authoritative implementation exists.
- `LEGACY`: compatibility code remains during an explicit migration window.
- `BROKEN`: an implemented path is known to fail its intended behavior.
- `MISSING`: no meaningful implementation exists.

No capability is marked production-complete merely because a page or schema
exists.

Statuses in this ledger are intentionally stricter than feature-development
statuses:

- `IMPLEMENTED + VERIFIED`: repository behavior passed its named reproducible
  check in this review.
- `IMPLEMENTED + UNVERIFIED`: code exists, but its strongest required check has
  not passed for the release candidate.
- `PARTIAL`: a required implementation or end-to-end path is incomplete.
- `MISSING`: no production implementation exists.
- `BLOCKED — EXTERNAL`: repository work is present, but provider, hosted
  infrastructure, policy, legal, or operational evidence is unavailable.

## Initial P0 dependency order

1. Harden privileged authentication with canonical MFA.
2. Add the canonical feature-flag domain because configuration and controlled
   rollout depend on it.
3. Add the missing support domain/workspace rather than treating support as a
   generic administrator.
4. Finish API-mode Web adapter coverage and contract tests without weakening
   deterministic Demo Mode.
5. Close canonical offer/moderation/appeal and notification delivery gaps.
6. Add search indexing, analytics taxonomy, caching policy and observability
   foundations.
7. Finish only repository-controlled provider behavior; keep release blocked
   until real vendor, legal and infrastructure evidence exists.

## Initial release blockers

The following cannot honestly be classified as complete at audit start:

- no production-certified KYC, business-registry, AI, email, SMS, push or
  search provider;
- no real Stripe/Connect/Identity sandbox evidence, dispute/chargeback
  certification or period-close reconciliation evidence;

## Final release blockers

The former repository-owned Solutions blocker is closed: API mode now uses the
canonical OpenAPI, backend service/repository, market-scoped PostgreSQL catalog,
and HTTP adapter. Production intentionally starts with an empty catalog rather
than copying demo fixtures.

Database rollout remains **NO-GO**. A fresh replay stops in already-versioned
migration `00030`, followed by known compatibility defects in `00032` and
`00040`. The Data/Platform owner must export the intended environment’s
`supabase_migrations.schema_migrations` ledger and checksums, reconcile it with
the repository, approve a forward-compatible baseline repair, prove a clean
Supabase-equivalent replay, run real-role RLS probes, and regenerate
`backend/src/generated/database.types.ts`. Editing applied history or
hand-writing generated types is prohibited.

No source change can legitimately replace the following evidence:

- production-certified KYC, business-registry, AI, email, SMS, push,
  geocoding, malware-scanning and any external search provider selected for
  launch;
- Stripe/Connect/Identity sandbox certification, dispute/chargeback drills and
  reconciled finance period-close evidence;
- a clean live PostgreSQL/Supabase application through migration 00088 on the
  intended engine, followed by query-plan and RLS smoke evidence;
- deployed backup/object-storage restore evidence with measured RPO/RTO, plus
  log/trace drains, dashboards, alerts and on-call notification delivery;
- legal and operations approval for DSA/DAC7/trader traceability, retention,
  invoicing, tax and regulated money-flow decisions;
- the English catalogue/localized route programme, if English is to be exposed;
- deployed API-mode staging E2E with the selected provider credentials.

split-application origins are absent, Web/mobile demo modes or mock Web storage
are selected, secure cookies are disabled, or live provider choices are
inconsistent. The staging certificate also refuses skipped application hosts.
These blockers therefore remain visible instead of silently falling back to
demo behavior.
